# Brookfield Comfort — Internal Platform (CLAUDE.md)

Guidance for Claude working in this repo. Conventions live in `docs/API-RULES.md` (authoritative). The code is stable and shipped — **read the code for how a feature works**; this file is the domain "why" and the DB landmines that aren't obvious from code. Build specs were retired once modules shipped (recoverable in git history if a big new job needs one).

## What this is

A **modular internal platform** for Brookfield Comfort (UK footwear e-commerce — mostly Birkenstock, sold on Shopify & Amazon). Login → dashboard of modules. Every module is a tile on the dashboard (`bcweb-web/src/app/dashboard/page.tsx`). The shell (auth, dashboard, nav, API envelope, DB pool) is module-agnostic.

## Structure — two apps in one repo

```
bcweb-server/   Express API — owns the Postgres connection and ALL SQL. Runs on a VPS (PM2).
bcweb-web/      Next.js 16 (App Router, src/app, TS, Tailwind 3) front end. Deploys to Vercel. Data fetching is SWR via
                src/lib/useApiQuery.ts — never in a useEffect (see docs/maintenance-notes.md).
docs/           API-RULES.md (authoritative conventions), deploy.txt (deployment procedure ONLY), crontab.txt (an EXACT copy of the VPS

                so add nothing to it; pull in UTF-8: `ssh root@vps "crontab -l" | Out-File -Encoding utf8 docs/crontab.txt`),
                maintenance-notes.md (dependency landmines, the no-fetching-in-effects rule, build gotchas),
                shopify-theme-edits.txt (THE one record of every change made to the Shopify theme — re-apply from it after a
                theme change / Dawn update; add any new theme change there), legacy PowerBuilder/DB reference.
```

The web app **never** connects to Postgres — only the server does. Web → HTTP (axios) → server → PostgreSQL (`brookfield_prod`, the same DB the owner's Python scripts use).

**The dashboard (2026-10-26, owner: "daily to be the main thing so its clear what to work on ... i dont want duplicates"):** a **Daily** hero first — Sales (today's profit), Pricing (Shopify due · Amazon due, from the in-stock lists), Ordering (Amazon Order · Shopify "sizes sold out" → Shopify Order's **Sellers** view, 2026-10-27: one row per non-Birkenstock size sold on Shopify in 30 days, `routes/shopify-sellers-list.js`; MISSED (on screen **Sold out**, 2026-10-27) = no local stock, nothing on local order AND none at/heading to FBA — FBA counts as cover, the team can pull from it; a dud SIZE can be marked **Don't order** (`shopify_dont_order`, `migrations/20261027_shopify_dont_order.sql`) — out of Missed until it sells again on Shopify, never Can't get, which is style-wide; the old style-block screen is the **Sizes** view, `?view=sizes`, one shared basket; Birkenstock is left out of BOTH views), **Selling** (2026-11-06 — one card, the two figures to keep AS HIGH AS POSSIBLE, owner: "Do one, will help the other": New stuff % of new SKUs sold → New Additions, and **Range** % of every size we hold sold in 90 days → the Slow movers front screen; Slow movers left the menu for it; Clearance is NOT on Daily — "a different thought"), Prospects, **AMZ loaded** (styles due a look) (the product search sits above it), then **every other screen ONCE** in six group tiles (Operations, Pricing, Products & stock, Birkenstock, Google, Admin) — no heading over them. ## Domain "why" — Shopify/Amazon Pricing

**Business context:** ~95% of Shopify sales are Birkenstock, which **cannot be re-ordered on demand** (ordered ~6 months ahead; stock in hand is all there is). There is no "sold out → restock" lever — **the job is to squeeze maximum margin from stock already held.** A fast-selling style with thin stock is a **price-up / harvest** candidate, NOT a restock flag.

**The Shopify Pricing and Amazon Pricing HOMES (`/pricing`, `/amz`) are ONE LIST of everything in stock** (2026-10-26, owner: "shouldn't go off segments — just be a list of all, with a due and not due toggle") — they redirect to `/pricing/all?by=all` / `/amz/all?by=all` (`routes/pricing-all-list.js`: Shopify-live styles with local stock; `routes/amz-all-list.js`: SKUs with FBA stock live or on its way in, shown "4 +6" (2026-10-29) — **each PLUS every row of that channel's Repricing status lists, 0-stock included** (2026-10-28, owner: "dashboard should cover everything" — Daily's Pricing counts read these, and missed 0-stock styles Repricing showed as Due)), unsplit, the usual Due switch; the segment pickers are gone (git history). Repricing still works from groups: a **segment**, or (Shopify only, 2026-09-23) a **Google campaign** bucket (`skusummary.googlecampaign`; the Segments screen's Segment | Campaign switch, `pause`/blank hidden; `utils/pricingGroup.js`), or a **Status** (Shopify AND Amazon, 2026-09-24 — the stored `skusummary.portfolio_status` WINNERS | STEADY | NEW | LOSERS, set by "Update now" on the Repricing Status tab, rules in `utils/portfolioStatus.js`; a WINNER is 12m revenue NET OF RETURNS > £1,500 — the top-20% line of selling styles (owner, 2026-10-12: "that 20% I want to keep feeding"; a FIXED bar, re-measured on request with `node scripts/winner-bar-review.js`, never live) (net since 2026-09-26 — "100 sold and 90 returned is a mess, not a winner") — NO SEASON TEST and NO HARVEST status since 2026-09-26 (owner: "Winners are our 12 month winners. ## Domain "why" — Amazon size history (2026-11-03)

`amz_size_history` keeps **price + FBA stock (live / inbound / total) for every Amazon size over time**, because `amzfeed` only knows today and pricing couldn't tell "out of stock" from "didn't sell at that price" (IVES-WHITE-06's dead Dec–mid-Mar looked like a stock-out; the Inventory Ledger later showed ~28 pairs at FBA all winter — it sat at £41.29 while its sister sizes sold at £39.99, then sold 13 in a week at £36.99; the Business Report for that winter shows the real cause — we held the Buy Box only ~4.5% of the time on it, with the most sessions of any White size). Rules in `utils/amzSizeHistory.js` + `migrations/20261103b_amz_size_history.sql` (owner decisions, read before changing): written in the same transaction as every amzfeed STOCK write (since 2026-11-09 those are the SP-API reads — see "Amazon SP-API" below; the quick read passes `carryInbound` so unseen sizes keep their last inbound), behind a SAVEPOINT (a history failure is reported, never fails the write); **change-only rows** (a size's value on a day = its latest row on or before it); **reserved left out** (moves daily, total includes it); **at most one row per size per day** (a later import replaces the day, a revert removes it); **3 years**, purged by the import as it writes (the row in force at the cut-off survives); `amz_size_history_run` = one line per import day. **Not forgotten:** a status line on Update Amazon and a dashboard warning shown only after 3+ days with no inventory import (`GET /amz-import-last → history`). **The past is rebuilt from Amazon's Inventory Ledger** (detailed view, manual CSV download, 18 months): `scripts/amz-ledger-backfill.js` writes rows labelled `source = 'ledger'` (`migrations/20261103c_amz_size_history_ledger.sql`) — **total only** (live / inbound / price NULL), SELLABLE movements summed **per day**, walked back from today's `amztotal` (NOT `amzlive`, which sends sizes below zero), only for days before the first import row; dry run by default, `--commit` to write; re-running replaces every ledger row. Past prices come from `sales.soldprice` + `amz_price_log`. All SKUs recorded; analysis (seasons, best price for revenue vs profit) is a later step.

## Domain "why" — Amazon pricing standard (`/amz-pricing` skill, 2026-11-04)

A repeatable verdict + suggested price for every Amazon SIZE, **judged against its sister sizes** (owner decisions one at a time, 2026-11-04 — rules and every number in **`utils/amzPricingStandard.js`**, THE copy; read its header). In short: window = the size's current price period (7 days – 12 weeks, sisters over the same days) · only in-stock days count (from `amz_size_history`) · a nudge within 2% doesn't restart the window (the team nudges sizes up while they sell) · **Buy Box first** (a supplied Business Report, < 50% = LOST BUY BOX, no price suggested and **no step rule** — the human decides from the row, which still compares it with its contested sisters and shows pairs a week, weeks of stock left and the next 4 weeks' profit) · expected pairs = style pairs × normal 12-month share, under 5 = can't tell · under ½ / over 1½× · ±2% of the in-stock sister median · verdicts LOST BUY BOX / TOO HIGH / NOT PRICE / LEAVE / ROOM TO GO UP / CAN'T TELL · **Lean** (default, per style by hand) and **Push** suggestions · **never below the £3-a-pair walk-away price** (no Buy Box race to the bottom) · the verdict ignores review dates, but **which sizes get checked follows the team's Amazon Due list** (2026-11-04, owner: "same system as our manual due dates" — `--top` by 12-month sales showed the same Ives colours every time): `amz-pricing-check.js --due` = the screens' Due predicate (`dueStyles`), top sellers in 28 days first; `--all` overrides Due (parked sizes too); a price set by the skill parks the size 7 days, an agreed "leave" 3 days (`scripts/amz-review-set.js` → `utils/amzReviewWrite.js`, THE W-A2 write, shared with `POST /amz-review`), a later date kept on a leave; CAN'T TELL stays Due. **Phase 1 is a skill** (`.claude/skills/amz-pricing`: `scripts/amz-pricing-check.js` READ ONLY; `scripts/amz-price-set.js` sets ONE owner-agreed size through the shared W-A1 write — dry run by default, `--commit`, `--by` + `--note` required, refuses >15% moves, under the walk-away, over RRP or a size already in the upload basket unless flagged) run on request while the verdicts are checked against the owner's judgement; a Pricing screen reading the same util comes once trusted. No nightly job (sales/stock change only on Update Amazon). The Business Report is supplied per analysis; storing it (Custom Analytics, which replaces Business Reports at the end of 2026) is a later decision.

## Schema landmines (legacy DB — respect these)

- **Price columns on `skusummary` (`shopifyprice`, `cost`, `rrp`, `minshopifyprice`, `maxshopifyprice`) are `character varying`, not numbers** and can hold junk (e.g. `maxshopifyprice='RRP'`). Read via `utils/sql.js → safeNumeric(col)` (NULL on non-numeric), never a bare `::numeric` (throws). **Write `shopifyprice` as a 2dp STRING** (e.g. `'36.95'`).
- **Never read stock from `skusummary.stockvariants`/`variants`** (stale). Current sellable stock = `localstock` where `ordernum='#FREE' AND COALESCE(deleted,0)=0 AND qty>0`. `localstock` holds in-stock rows only — for the full size range use **`skumap`** (one row per variant), LEFT JOIN sellable stock, default 0.
- **Size = the code's suffix after the last `-`** — SQL `SUBSTRING(code FROM '[^-]*$')`. **Not `RIGHT(code,2)`**: ~10% of live codes are half sizes (`…-37.5` → `.5`, so 37.5/38.5/40.5 merged into one size) and some brands use UK sizes (`…-8` → `-8`). Sort numerically with `~ '^[0-9]+([.][0-9]+)?$'` → `::numeric` (write `[.]`, not `\.`, inside a JS template string).
- **`skusummary.colour` is an overloaded segmentation tag** (ambiguous). Use `title.shopifytitle` for a human name.
- **Dates:** legacy `created`/`updated` are TEXT (`'YYYYMMDD HH24:MI:SS'`, Europe/London). Prefer the newer `created_at timestamptz` / `changed_at timestamptz` for real date logic but keep writing the legacy text stamps too. Never hand a pg `DATE` to `toISOString()` (parsed as local midnight → BST shifts the day back one); cast to text in SQL.
- **Order Status:** `orderstatus.orderdate` is `character varying`; an un-placed row is `''` **or NULL** — always test `COALESCE(orderdate,'')=''`. `orderstatus` has **one row per physical unit** (`qty` always 1); quantities are `COUNT(*)`, +/− means insert/archive whole rows. Order cost = `skusummary.cost` via `safeNumeric`, never `skumap.cost` (blank/placeholder on many rows). Barcode = `skumap.ean` with the trailing `B` stripped. The module is two stages split on the `orderdate` marker: TO PLACE (`orderdate=''`, chosen, not yet bought) → ON ORDER (`orderdate<>''`, with the supplier). `utils/orderStatus.js` owns the predicates. Scope = supplier orders only (`ordertype` 2 local, 3 Amazon); customer orders (`ordertype=1`) never touched.

## Conventions (full detail in docs/API-RULES.md)

- **Every API response is HTTP 200 + a `return_code`** (`SUCCESS` or an error code). **Never** 4xx/5xx for API-level errors.
- **One route file per endpoint** in `routes/` (kebab verb-noun), structured header block, heavily commented (explain *why*). `utils/apiLogger.js` logs every route.
- **JWT carries only `{ id }`.** `middleware/verifyToken.js` → `req.user = { id, display_name }`. `changed_by` is resolved server-side, never sent by the client.
- **DB:** central pool in `database.js`; `utils/transaction.js → withTransaction` for writes; parameterised queries only; no N+1.
- **Frontend client (`src/lib/api.ts`) never throws on API-level errors** — returns `{ success, data?, error?, return_code? }`; only network failures throw. Auth in `src/contexts/AuthContext.tsx`.
- **No hard-coded secrets** — everything via `.env`; flag if a new var is needed.
