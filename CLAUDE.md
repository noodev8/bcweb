# Brookfield Comfort — Internal Platform (CLAUDE.md)

Guidance for Claude working in this repo. Conventions live in `docs/API-RULES.md` (authoritative). The code is stable and shipped — **read the code for how a feature works**; this file is the domain "why" and the DB landmines that aren't obvious from code. Build specs were retired once modules shipped (recoverable in git history if a big new job needs one).

## What this is

A **modular internal platform** for Brookfield Comfort (UK footwear e-commerce — mostly Birkenstock, sold on Shopify & Amazon). Login → dashboard of modules. Shipped modules: **Shopify Pricing, Amazon Pricing, Inventory, Order Status**. The shell (auth, dashboard, nav, API envelope, DB pool) is module-agnostic.

## Structure — two apps in one repo

```
bcweb-server/   Express API — owns the Postgres connection and ALL SQL. Runs on a VPS (PM2).
bcweb-web/      Next.js 16 (App Router, src/app, TS, Tailwind 3) front end. Deploys to Vercel. Data fetching is SWR via
                src/lib/useApiQuery.ts — never in a useEffect (see docs/maintenance-notes.md).
docs/           API-RULES.md (authoritative conventions), deploy.txt (deployment procedure ONLY),
                maintenance-notes.md (dependency landmines, the no-fetching-in-effects rule, build gotchas),
                legacy PowerBuilder/DB reference.
```

The web app **never** connects to Postgres — only the server does. Web → HTTP (axios) → server → PostgreSQL (`brookfield_prod`, the same DB the owner's Python scripts use).

**The dashboard (2026-10-26, owner: "daily to be the main thing so its clear what to work on ... i dont want duplicates"):** a **Daily** hero first — Sales (today's profit), Pricing (Shopify due · Amazon due, from the in-stock lists), Ordering (Amazon Order), New stuff (new sizes not sold yet → New Additions), Prospects, **AMZ loaded** (styles due a look) (the product search sits above it), then **"Everything else": every screen ONCE** (Operations, Pricing, Products & stock, Birkenstock, Google, Admin). Don't add a screen to two groups or repeat a Daily screen in the menu. `/daily` redirects to the dashboard.

```
cd bcweb-server && npm run dev   # API on :3020 — reads bcweb-server/.env (DB_* + JWT_SECRET)
cd bcweb-web    && npm run dev   # Web on :3000 — reads bcweb-web/.env (NEXT_PUBLIC_API_URL)
```

Start the API first. Seed/reset a user: `node scripts/seed-user.js <username> <password> Andreas`.
Deployment: `docs/deploy.txt` (server → VPS/PM2 rsync; web → Vercel, behind the app login).

## Domain "why" — Shopify/Amazon Pricing

**Business context:** ~95% of Shopify sales are Birkenstock, which **cannot be re-ordered on demand** (ordered ~6 months ahead; stock in hand is all there is). There is no "sold out → restock" lever — **the job is to squeeze maximum margin from stock already held.** A fast-selling style with thin stock is a **price-up / harvest** candidate, NOT a restock flag.

**The Shopify Pricing and Amazon Pricing HOMES (`/pricing`, `/amz`) are ONE LIST of everything in stock** (2026-10-26, owner: "shouldn't go off segments — just be a list of all, with a due and not due toggle") — they redirect to `/pricing/all?by=all` / `/amz/all?by=all` (`routes/pricing-all-list.js`: Shopify-live styles with local stock; `routes/amz-all-list.js`: SKUs with FBA stock), unsplit, the usual Due switch; the segment pickers are gone (git history). Repricing still works from groups: a **segment**, or (Shopify only, 2026-09-23) a **Google campaign** bucket (`skusummary.googlecampaign`; the Segments screen's Segment | Campaign switch, `pause`/blank hidden; `utils/pricingGroup.js`), or a **Status** (Shopify AND Amazon, 2026-09-24 — the stored `skusummary.portfolio_status` WINNERS | STEADY | NEW | LOSERS, set by "Update now" on the Repricing Status tab, rules in `utils/portfolioStatus.js`; a WINNER is 12m revenue NET OF RETURNS > £1,500 — the top-20% line of selling styles (owner, 2026-10-12: "that 20% I want to keep feeding"; a FIXED bar, re-measured on request with `node scripts/winner-bar-review.js`, never live) (net since 2026-09-26 — "100 sold and 90 returned is a mess, not a winner") — NO SEASON TEST and NO HARVEST status since 2026-09-26 (owner: "Winners are our 12 month winners. Price them any time. But ordering should be against what is actually available" — season left the status, HARVEST was retired, its out-of-season non-sellers are LOSERS; don't put a season test back without the owner); an Amazon SKU takes its style's status; the FIRST and DEFAULT tab on the Repricing screen, Status | Segment | Campaign — bare `/segments` opens it, the segment view is `?by=segment`). **A status list is ONE unsplit list, OUT OF STOCK INCLUDED** (`routes/pricing-status-list.js` styles / `routes/amz-status-list.js` SKUs: every style/SKU with the status, no Selling/Stuck bars — owner: "not much point in splitting" — and 0-stock rows listed so prices can be set ahead of stock arriving, "don't want to leave them at old clearance price"). The segment/campaign lists still require stock. **Each style also carries a stamped LEAD CHANNEL** (`skusummary.portfolio_channel` SHP | AMZ | BOTH: ≥80% of 12m revenue on one channel, else BOTH; unsold = BOTH if on Amazon else SHP; NULL reads as BOTH) — the status stays one all-channel tag, but a channel's status lists (and Repricing tiles) show only its own + BOTH styles (`utils/portfolioStatus.js → channelFilterSql`, the one predicate). Why: 23 of 73 winners were Amazon winners earning ~2.5% on Shopify. **The Winners screen was RETIRED 2026-09-25 and folded into the Repricing Status tab** ("the same screen for two different points of view" — repricing, and analysing winners; the dashboard Winners card and `/analytics/winners` redirect to `/segments`). That tab shows a Shopify row and an Amazon row of four tiles — each tile's number is STYLES (Amazon too), its due line is styles due (an Amazon style is due if ANY size is) — with **no cross-channel total anywhere** (BOTH styles overlap; owner wants the channels split cleanly). A tier toggle (£1,500/2,500/5,000/10,000, `?bar=`) is a LOOKUP WITHIN THE TAG: it narrows only the WINNERS tiles (stamped all-channel revenue) and dims the other six — a hidden winner has no known other status, and storing a fallback status was rejected. Winners by brand sit inside each WINNERS tile. There is NO status trend: it was removed 2026-09-25 (graph + `portfolio_status_snapshot`), because (while a winner had to be in season) the line charted the calendar and season edits, not the business. Seasons are set in bulk on **Products & stock → Seasons** (`/seasons`) — season now feeds only Inventory's WINTER/SUMMER commands and the Google Ads season filter. **Ordering uses "Can't get it" instead** (`utils/noSupply.js`, `skusummary.no_supply_*`): a STYLE fact, not a channel one, that hides a style from the order screens for 3 months then lapses; on screen the pair is **Can't get / Release** — never park/unpark, because "parked" already means a pricing review date. Managed on Shopify Order, Amazon Order and Seasons' Can't get view — one flag, a style marked on either order screen is off both. On Amazon Order (2026-09-27) a marked size stays visible while it has local stock, because it can still be PICKED to FBA ("we can get them because we have them"); the rate fill leaves its Order half empty and still fills Pick. **Repricing does NOT link to the order screens** (removed 2026-10-08, owner: "The winners screen should be about pricing only"): the status lists' "Stock & order" links and both order screens' `?status=` arrival (the "Repricing: Winners" chip) are gone — Shopify Order and Amazon Order always open on everything. Amazon Order's own presets are on screen **Hot | Warm | Simmer** (Hot = the top 20% of sizes that sold in 30 days, by profit — computed live, 2026-10-12; Warm = not Hot, > £3/unit, sold in 6 months; **Simmer** (2026-10-21, replaced Cold) = not Hot, > £0 and ≤ £3/unit, sold in the last 30 days NET (`units_30d > 0`; was 6 months until 2026-10-22 — owner: sizes that sat for months at the low price aren't to be ordered again; how FAST a size sold is a planned separate fast-seller pricing screen, not Simmer's job), FBA TOTAL 0 — thin-margin fresh sellers to price up towards £3 and try with 1 unit (a "£3 price" column/button from `utils/amzProfit.js → priceForProfit`, and a "1 each" fill in Boost's slot); losses left out on purpose, owner: "we dont want to order losers"; bars in `utils/portfolio.js`) (were Winners | Potential | Recycle — renamed so "Winners" only ever means the portfolio status). Status **replaced Top earners**, which was removed entirely on 2026-09-24 (tab, cards, route, grouping — git history if ever wanted). Same styles, bars, drill and writes — only the slice differs. Then a **WINNERS | LOSERS** switch:

> **UI names (owner, 2026-09-23):** on screen, WINNERS | LOSERS are **Selling | Stuck** (| Both), and the `/segments` screen is **Repricing** (nav, tile, title, back links). Labels only — routes, `?mode=winners|losers|all`, API/route names and code identifiers keep the old words. "Winners" in the UI now means ONLY the portfolio WINNERS status (its tiles on Repricing's Status tab); don't reintroduce it for the Selling | Stuck lists.
- **WINNERS** — in-stock, un-parked styles that sold **≥2 units in 30d AND averaged ≥£2 realised net profit per unit** (`AVG(sales.profit)`), best sellers first → price **up** / harvest. Drop 0-stock and "parked" styles.
- **LOSERS** — in-stock, un-parked stock that sold **nothing in 30d**; most stock first → price **down**. That single test is the whole membership rule.
- Both bars are **identical on Shopify and Amazon** (owner's call — one team-wide definition), differing only in grain. They are named constants in the route files, **not** query params yet. The old LOSERS machinery (90d window, `cover ≥ coverWeeks`, `cover_weeks`/`is_dead`/`u90`/`u14` fields) was removed in the 2026-07-29 simplification — the route headers record the accuracy trade-off that was knowingly accepted, read those before reinstating any of it.
- A style/SKU that sells 1 unit, or sells well on thin margin, is now on **neither** list. That gap is known and deliberate; it is another module's job, not something to "fix" here by loosening a bar.
- **Lists are the whole qualifying set, not a top-N** (the tab count IS the job; it shrinks as cleared). `limit` survives only as a safety cap (`utils/listLimit.js`, default 100 / max 500); routes return `total` + `truncated`.
- **Drill-down** shows header + pricing timeline (one row per distinct price, with pace `/wk`) + size curve. Pace = `units / max(span_days,7)/7 weeks`, computed app-side. Size curve shows ALL sizes (0 for sold-out) as a guardrail before a cut.

**Review cooldown (`next_shopify_price_review`, a date):** while future, the style is hidden from triage. A review period is **optional** on a price change (a "None" chip leaves the review date untouched). Suggested review defaults: raise ~7d, cut ~14d, hold ~30d (suggestions, editable).

**Shopify and Amazon prices are INDEPENDENT (2026-09-15, owner).** The old "match Amazon price" autopilot — `skusummary.match_amazon_price` + the `C:\scripts\amz-match` cron, which pinned a flagged style's `shopifyprice` to Amazon's cheapest in-stock size — is **retired, not deleted**: the crontab line is rem'd out, `migrations/20260915_amz_match_disable.sql` set the column back to `false` on every row, and the UI is hidden behind `bcweb-web/src/lib/features.ts → AMZ_MATCH_UI`. The panel, `pricing-match-toggle`, the `MATCH_LOCKED` branch in W1 and the list badges all stay and revive by flipping that flag. **Don't "fix" the dead badges or re-point Shopify at Amazon.** Why: Amazon prices per SIZE (IVES WHITE ran £37.30–£41.09), so there is no single Amazon price and the rule let one thin size set the style's price; and the same price is worth ~2× more on Shopify (no referral fee — £39.29 nets £9.06 there vs £4.86 booked on Amazon), so matching down gave away the margin that funds Google Shopping. Amazon is now **shown, never obeyed** — `pricing-drill` returns the live spread (`amazon_lowest`/`amazon_highest`/`amazon_live_total`) plus per-size `amz_price`/`amz_live` on `sizes[]`; the setter carries the spread and a note when you go under Amazon's lowest. **All advisory — nothing blocks.** **Shopify vs Amazon** (`/pricing/vs-amazon`, `routes/pricing-vs-amazon.js`, 2026-10-07) is the list view of that spread: every style with a size live on Amazon, gap = Shopify − Amazon HIGHEST (owner's floor: Shopify never under Amazon's dearest live size — Amazon can pull the Buy Box when it sees the item cheaper elsewhere), red/amber/green, worst first. It is a manual tool, not the autopilot back: each Apply (or the bulk "Set to Amazon high") is a plain W1 with the note **"Amazon Match"** and a **10-day review — unless the style already has a LATER review date, which is kept** (owner: a style parked for months, e.g. Summer stock in October, was parked on purpose; the lift is a Buy Box fix, not a sales test). The list ignores the review cooldown on purpose.

**Amazon** mirrors Shopify but at **SKU grain** (`code`, not `groupid`); reads `amzfeed` (FBA-only, **READ ONLY**) for live price/stock. **No live push** — apply only logs to `amz_price_log`; the price reaches Amazon via a client-built Seller Central upload file (rolling 12h team-wide basket, rebuilt from the log). Amazon "margin" is net (price − cost − FBA fee).

**Fast sellers** (`/amz/fast`, `routes/amz-fast-sellers.js`, 2026-10-22; a tile in the dashboard's **Pricing** group, NOT linked from the `/amz` home — owner: "under pricing for now - not through Amazon") — an Amazon PRICING list (not ordering; Simmer on Amazon Order is the "order 1" view): every size with a net sale in 30 days, any margin, any stock, with **Priced→sold** (days from the price the last sale went at going live — `uploaded_at`, else `changed_at` — to that sale; holds skipped) and **Shipped→sold** (from the last `amzshipment_archive` row, kept 60 days). Rules live in **`utils/sellSpeed.js`** — computed live, nothing stored. Owner's calls: no speed cutoff (sorted, fastest first), **no review cooldown** (a size priced there stays, with a Last priced column), Set reviews **7 days or keeps a later review date**, note "Fast sellers", **no £3 price** (that is Simmer's ordering bar; the aim here is as much as a fast seller will take — RRP is shown, no gap column), and the list refreshes **only on the Refresh button** (SWR auto-revalidation off for that key; a row's × cuts it from the screen until the next Refresh — nothing stored). Why: the Rieker X9165-00-38 sold at £1.91 a unit the day it was priced to the Buy Box — a size that fast at that price can take more.

## Domain "why" — Pricing Slider (`/slider`, 2026-10-17)

A **group** of products whose price steps DOWN by a % of RRP every N days until each one **sells — then it HOLDS** at that price (the "diamond") — or reaches the floor. Why: dropping NEW stock straight to the bottom found some diamonds but sold others at a loss, and gave the diamonds away below what they'd have sold at. Rules live in `utils/slider.js` (read its header before changing anything): one channel per group (Shopify per STYLE, Amazon per SKU); step = % of the RRP it joined with (fixed £, so the floor date is predictable — compounding was rejected); floor = any % of RRP the human picks, plus an optional break-even floor (ticked by default on a new slider since 2026-10-20; owner: "they might just want to clear some rubbish too"); found after 1/2/3 sales (between the 1st and Nth a sale HOLDS the price another interval); first move due straight away (with Start from RRP the first move is the lift to RRP); due in Europe/London DAYS. **NO CRON — every price move is a button press** on the group page, like normal pricing; Amazon moves go into the team upload basket and count from upload. Review dates are NOT touched — a badge on the pricing screens is the indicator. No price-ending snapping, no Shopify-vs-Amazon checks. Tables `slider_group` / `slider_member` (`migrations/20261017_slider.sql`; the `slider_event` log was dropped 2026-10-20 — owner: "We dont need a log" — the price logs and bclog already record every move); a partial unique index = one LIVE (sliding/found/floor) slider per product per channel. Prices go through the shared W1/W-A1 writes (`utils/priceWrite.js`) — never a copy. Built 2026-10-17 in four phases: groups/add/remove/reset, Shopify stepping, Amazon stepping with the basket, and **badges on the pricing screens** (`GET /slider-marks` → `components/SliderBadge.tsx`: one SWR-cached lookup shared by the Shopify/Amazon lists, Find, Shopify vs Amazon, and a warning line above the price setter on both drills; Amazon Order carries both — the badge by the SKU and the warning in the detail row's price box, 2026-10-22 — pricing a slider product by hand takes it out at the next Move). **Amazon moves count from the upload**: a move is live once `uploaded_at` is stamped OR amzfeed shows the new price (the team often uploads without pressing "I've uploaded"); still in the 72h basket = waits; aged out un-uploaded = the move didn't happen (undone at the next press). Amazon "priced by hand" is read from `amz_price_log` (a newer row at another price), never from the feed, which can predate an upload. **Out of stock WAITS** (no cut while it can't sell; due the moment stock arrives) and **no catch-up** (a late press makes one move) — owner, phase 2. What a press does to each product is ONE function, `utils/slider.js → decide()`, read by the screen and re-read by the step inside its transaction.

The team's shared notepad for **mining NEW products on Amazon** (Back Office tile). One line = one style: Amazon link → ASIN (the screen fills the name from the URL slug and keeps only the ASIN), owner = who added it, gut rating Diamond/Good/Sketchy, RRP (free text, to guess the profit). **Checks** = rank + price **typed by hand, free text** ("58k") — no scraping, no API, and **no rank comparison** (owner reads changes by eye in History). They will press delete"; one button, no separate Archive): **Ordered | Dropped** ARCHIVE the line ("so that colleagues know a decision for a prospect and check if we've tested this style"), **Delete for good** really deletes; an optional reason, written as the line's last comment; checks and comments kept; read-only on the screen's **Active | Archive** switch. **Kept 6 months, no cron** — every add and every archive purges older ones (`utils/prospect.js → purgeOldArchive`). Pasting an archived ASIN says **TESTED BEFORE** and offers **Reopen** (one line per style; save refuses a second line). Daily's Prospects count is active lines only. "Delete for good" is a real delete (CASCADE, nothing kept). Columns `archived_at` / `archived_by` / `outcome` (`migrations/20261026_prospect_archive.sql`). The only link to our stock is the **DUPLICATE** badge/warning (ASIN on the list already, or in `amzfeed` — FBA listings only); "NEW TO US" and the catalogue search were removed on purpose. **No links to pricing or ordering, no sales figures** — research stays apart from managing existing stock. Tables `prospect` / `prospect_check` / `prospect_note` (`migrations/20261021_prospects.sql`).

## Domain "why" — AMZ loaded (`/amz-loaded`, 2026-10-26)

Every style held locally (sellable `localstock`) with **no size on Amazon** — no `amzfeed` row for its groupid, i.e. no SKU / FNSKU there (amzfeed lists every FBA listing, 0-stock ones too; `skumap.fba` is the FBA FEE, not an FNSKU) — **Birkenstock left out** (brand `ILIKE 'birk%'`). The job: decide whether to list it. **Reviews like prices**: ticking styles and setting a review (or Clear review) stamps `skusummary.next_amz_load_review` (its own column — `migrations/20261026_amz_load_review.sql`; never touches a price review, no log row) and hides the style from the Due view until then. **Clicking a style opens its sizes** (owner: "easy able to check amz ranking"): every live `skumap` size with its barcode (`ean`, trailing B stripped) — one click copies it (no Amazon search links: "just give me the barcodes to copy") — local stock, the **Amazon upload file** button (the same listing loader as Add / Modify — `components/AmazonExport` → `POST /product-amazon`, which also stamps the sizes' skumap sku/status), and the review control. The review UI is the pricing screens' own (Due switch, "Review in (None) 3…90 days" + Set review, amber date chip in the Review column) so it reads as the same thing. `routes/amz-loaded-list.js` (READ ONLY) / `routes/amz-loaded-review.js` (WRITES that column only).

## Writes (exact — wrap each in `withTransaction`)

- **W1 — apply Shopify price** (`POST /pricing-apply`): `reviewDays` optional (integer ≥ 1, or omitted = leave review date untouched). Server-side bounds: **allow-but-flag `< cost`** (a hard block until 2026-10-11 — owner: "I need to apply any price I want") and **allow-but-flag `> rrp`**. Atomically `UPDATE skusummary SET shopifyprice=$price_string[, next_shopify_price_review=CURRENT_DATE+$reviewDays]` + `INSERT price_change_log (groupid,'SHP',old,new,NULL,$note,changed_by)`. **Do NOT set `shopifychange`.** After commit, W1 pushes to **Shopify immediately** (`utils/shopify.js → pushIfLive`, best-effort, never rolls back the DB; on failure `shopify:{pushed:false}` and operator re-Applies — `productSet` is idempotent). A **same-price Apply (a hold) pushes only if Shopify's live price differs** (`pushIfStale`, 2026-10-17) — that is what makes the re-Apply a real retry; before, a hold sent nothing and the retry was a silent no-op. **Google is DECOUPLED** — W1 does not push Google; a periodic sweep (`scripts/google-price-sweep.js`; `crontab.txt` is the definitive source for its schedule — don't restate it) finds un-sent SHP changes (`price_change_log.google_pushed_at IS NULL`, Google-live styles) and pushes each style's current price once via in-process Node (`utils/googleMerchant.js`, `utils/googleAuth.js`). It writes a **`salePrice`-only supplemental override** (Merchant API `products/v1`) so the primary feed's `price`/RRP is preserved. Nightly `merchant_feed.py --upload` (3:30am BST) is the ultimate backstop. Add/Modify (`product-price`) still pushes Google inline.
- **W2 — park only** (`POST /pricing-park`): `UPDATE skusummary SET next_shopify_price_review=CURRENT_DATE+$reviewDays`. No price change, no log row.
- **Bulk** on WINNERS/LOSERS lists (`BulkActionBar`): a bulk price move **loops W1 per row client-side** (so each live push fires and per-item bounds apply); bulk review-only uses `/pricing-park-bulk`. Amazon bulk loops `/amz-apply` and reuses `/amz-review`.
- **W-A1 — apply Amazon price** (`POST /amz-apply`): logs to `amz_price_log` only (flags `< cost+fbafee` — a hard block until 2026-10-11 — and flags `> rrp`; nothing blocks); optional `reviewDays` parks via `next_amz_price_review`. Never writes `amzfeed`.
- **W1 / W-A1 write cores are shared** (`utils/priceWrite.js → writeShopifyPrice / writeAmzPrice`, 2026-10-17): `pricing-apply`, `amz-apply` and the Pricing Slider all call them on their own transaction client, so a slider's member/event rows land in the SAME transaction as the price. The routes keep request validation, the post-commit Shopify push and the response.
- **W-S1 — Pricing Slider reset** (`POST /slider-reset`, one product per call, looped client-side): W1/W-A1 to RRP (note "Slider reset to RRP · <group>") + member `state='reset'`, one transaction; Shopify push after commit; Amazon returns the basket item. Add / remove / group edits write slider tables only, never a price.
- **W-S2 — Pricing Slider move** (`POST /slider-step`, "Move prices", one product per call, looped client-side): locks the member (+ the style row on Shopify), re-runs `decide()`, then either a price — W1 (push after commit) or W-A1 (into the upload basket; returns the basket item) — for a cut or the lift to RRP (note "Slider · <group> · step n" / "· back to RRP"; review date untouched), or a slider-only settle (found / hold / floor / repriced). An expired Amazon move is written back first. Nothing due any more = writes nothing, so a double press can't move a price twice.
- **W-C1 — collection tags** (`POST /collection-tag-set`, the **Collections** screen `/collections`, 2026-10-14; Slow's clearance buttons write through the same `utils/collectionTags.js`): the **DB is the record** of who is in which Shopify collection (`collection` = the tags, `collection_member` = one row per style per tag, **max 3 tags per style**) and Shopify carries a copy — each style's row and its `tagsAdd`/`tagsRemove` (that one tag only) change together, a Shopify failure rolls the row back. **Add needs `shopify = 1`; Remove always works** (switching Shopify OFF doesn't unpublish, so an OFF style keeps its tag on the store — the screen lists every tagged style whatever its flag). The owner builds each smart collection in Shopify admin and manages tags from BCWEB only — don't read tags back from Shopify or "sync" from it.
- **W-O1 — sync Shopify orders** (`POST /order-sync`, the **"Update orders"** button — legacy terminology, on both Analytics → Sales and Customer Orders, via the shared `bcweb-web/src/components/UpdateOrdersButton.tsx`; the route/util keep the `order-sync` naming): fetch outside the transaction, then all six phases inside one — orders → `orderstatus`, sales booked to `sales` (`SHP`, per-unit profit from `utils/shopifyProfit.js`), shipped orders → `orderstatus_archive`, pick allocation over `localstock`, then housekeeping. **⚠️ THIS LOGIC IS DUPLICATED IN `C:\scripts\orders\update_orders.py`, WHICH IS STILL IN CRON.** Both are live and write the same rows; a change to one and not the other leaves the DB written under two sets of rules with nothing recording which. Read the banner at the top of `utils/orderSync.js` before changing what a run does — and see `docs/order-sync-port.md` for the behaviour inventory. Needs `SHOPIFY_ORDERS_ACCESS_TOKEN` (a **different** token from `SHOPIFY_ACCESS_TOKEN` — `read_orders`, not `write_products`).

## Schema landmines (legacy DB — respect these)

- **Price columns on `skusummary` (`shopifyprice`, `cost`, `rrp`, `minshopifyprice`, `maxshopifyprice`) are `character varying`, not numbers** and can hold junk (e.g. `maxshopifyprice='RRP'`). Read via `utils/sql.js → safeNumeric(col)` (NULL on non-numeric), never a bare `::numeric` (throws). **Write `shopifyprice` as a 2dp STRING** (e.g. `'36.95'`).
- **Never read stock from `skusummary.stockvariants`/`variants`** (stale). Current sellable stock = `localstock` where `ordernum='#FREE' AND COALESCE(deleted,0)=0 AND qty>0`. `localstock` holds in-stock rows only — for the full size range use **`skumap`** (one row per variant), LEFT JOIN sellable stock, default 0.
- **Size = the code's suffix after the last `-`** — SQL `SUBSTRING(code FROM '[^-]*$')`. **Not `RIGHT(code,2)`**: ~10% of live codes are half sizes (`…-37.5` → `.5`, so 37.5/38.5/40.5 merged into one size) and some brands use UK sizes (`…-8` → `-8`). Sort numerically with `~ '^[0-9]+([.][0-9]+)?$'` → `::numeric` (write `[.]`, not `\.`, inside a JS template string). Fixed app-wide 2026-09-24.
- **`skusummary.colour` is an overloaded segmentation tag** (ambiguous). Use `title.shopifytitle` for a human name.
- **Dates:** legacy `created`/`updated` are TEXT (`'YYYYMMDD HH24:MI:SS'`, Europe/London). Prefer the newer `created_at timestamptz` / `changed_at timestamptz` for real date logic but keep writing the legacy text stamps too. Never hand a pg `DATE` to `toISOString()` (parsed as local midnight → BST shifts the day back one); cast to text in SQL.
- **Order Status:** `orderstatus.orderdate` is `character varying`; an un-placed row is `''` **or NULL** — always test `COALESCE(orderdate,'')=''`. `orderstatus` has **one row per physical unit** (`qty` always 1); quantities are `COUNT(*)`, +/− means insert/archive whole rows. Order cost = `skusummary.cost` via `safeNumeric`, never `skumap.cost` (blank/placeholder on many rows). Barcode = `skumap.ean` with the trailing `B` stripped. The module is two stages split on the `orderdate` marker: TO PLACE (`orderdate=''`, chosen, not yet bought) → ON ORDER (`orderdate<>''`, with the supplier). `utils/orderStatus.js` owns the predicates. Scope = supplier orders only (`ordertype` 2 local, 3 Amazon); customer orders (`ordertype=1`) never touched.

## Conventions (full detail in docs/API-RULES.md)

- **Every API response is HTTP 200 + a `return_code`** (`SUCCESS` or an error code). **Never** 4xx/5xx for API-level errors.
- **One route file per endpoint** in `routes/` (kebab verb-noun), structured header block, heavily commented (explain *why*). `utils/apiLogger.js` logs every route.
- **JWT carries only `{ id }`.** `middleware/verifyToken.js` → `req.user = { id, display_name }`. `changed_by` is resolved server-side, never sent by the client.
- **DB:** central pool in `database.js`; `utils/transaction.js → withTransaction` for writes; parameterised queries only; no N+1.
- **Frontend client (`src/lib/api.ts`) never throws on API-level errors** — returns `{ success, data?, error?, return_code? }`; only network failures throw. Auth in `src/contexts/AuthContext.tsx`.
- **No hard-coded secrets** — everything via `.env`; flag if a new var is needed.
