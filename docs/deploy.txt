  bcweb-server/scripts/amz-product/amz_upload_single.py  (+ SHOES.xlsm template beside it)
The VPS is otherwise pure Node, so this needs a one-time setup on the server:
  - Python 3 installed and on PATH (or set PYTHON_BIN in the prod .env to the interpreter path)
  - pip packages: openpyxl, psycopg2 (or psycopg2-binary), python-dotenv
  - the scripts/amz-product/ folder must survive the rsync (it does today -- only 'docs' etc. are excluded)
  - the helper reads DB creds from bcweb-server/.env (already present in prod)
When you deploy this the first time, ask Claude to help wire up the Python env + verify the button end-to-end.

== DONE 2026-07-26: upgraded Next.js 15 -> 16.2.12 (bcweb-web). NOT YET CLICK-TESTED -- see the checklist at the end.
Rationale was COMPOUNDING COST, not security: 15.5.22 was still the actively-backported line and still getting patches, so there
was no security argument and nothing was broken. But the migration surface only ever grows -- every module added on 15 is a module
that has to be re-verified on 16 later -- and it was as small as it would ever be. Did it early and deliberately, to build on 16.

WHAT CHANGED
  bcweb-web/package.json:      next ^15.5.20 -> ^16.2.12 | eslint-config-next ^15.5.20 -> ^16.2.12
                               REMOVED devDep @eslint/eslintrc | REMOVED override "brace-expansion" (see below -- important)
                               eslint STAYS on ^9.39.4 (see below) | overrides postcss + sharp both STAY
  bcweb-web/eslint.config.mjs: dropped the FlatCompat bridge; eslint-config-next@16 ships NATIVE FLAT CONFIG arrays
                               (core-web-vitals + typescript), imported and spread directly. Default imports, because the dist is
                               CJS `export =` which Node's ESM interop hands back as the array itself, not a {default} wrapper.
  bcweb-web/tsconfig.json:     REWRITTEN BY `next build` ITSELF, not by hand. It mandates "jsx": "preserve" -> "react-jsx" (React
                               automatic runtime) and adds ".next/dev/types/**/*.ts" to include. It also reflows every array onto
                               multiple lines -- cosmetic churn, don't bother reverting it, the next build just redoes it.
  UNCHANGED: next.config.js, postcss.config.js, tailwind config, and every page/component/<Image> call site.

!! THE "brace-expansion": "^5.0.8" OVERRIDE WAS NEVER A REAL FIX AND HAS BEEN REMOVED. READ THIS BEFORE RE-ADDING IT.
!! brace-expansion 1.1.x exports the function DIRECTLY (`module.exports = expandTop`). 5.0.8 exports an OBJECT
!! ({EXPANSION_MAX, EXPANSION_MAX_LENGTH, expand}). minimatch@3.1.5 does `var expand = require('brace-expansion')` and then calls
!! `expand(pattern)`. So forcing 5.0.8 into minimatch 3.x's declared "^1.1.7" slot makes minimatch throw
!! "TypeError: expand is not a function" -- it silences `npm audit` by BREAKING the library rather than patching it.
!! It appeared to work on Next 15 PURELY BY LUCK: minimatch 3.x short-circuits (`if (options.nobrace || !/\{...\}/.test(pattern))
!! return [pattern]`) and only calls expand() when the pattern ACTUALLY CONTAINS BRACES. Nothing in the old config array had any
!! (`.next/**`, `node_modules/**`). eslint-config-next@16's flat config declares files: ['**/*.{js,jsx,mjs,ts,tsx,mts,cts}'] --
!! braces -- so it detonated on the first file match and `npm run lint` died outright.
!! There is NO API-compatible patched version to use instead: latest of every major below 5 is 1.1.16 / 2.1.2 / 3.0.2 / 4.0.1,
!! and the advisory (GHSA-mh99-v99m-4gvg, DoS via unbounded expansion) covers everything <=5.0.7. The patch IS the breaking major.
!! ==> CONSEQUENCE, ACCEPTED DELIBERATELY: bcweb-web now reports 9 high dev-only advisories. `npm audit --omit=dev` is 0 --
!!     the SHIPPED BUNDLE IS CLEAN. The whole chain is lint tooling (eslint-plugin-import / -jsx-a11y / -react -> minimatch ->
!!     brace-expansion 1.1.16) that never reaches a browser, and exploiting it means feeding hostile glob patterns to your own
!!     linter. This is the one place in this repo where "dev-only" is the honest answer rather than an excuse, BECAUSE THERE IS NO
!!     FIX TO APPLY. Real fix is upstream: @eslint/config-array@0.21.2 still depends on minimatch ^3.1.5 (EOL). Re-check later.

!! ESLINT STAYS ON 9 IN bcweb-web (bcweb-server is on 10). This mismatch is deliberate -- do not "align" it.
!! eslint-config-next@16 advertises peer eslint ">=9.0.0", which looks like the 15-era blocker (peer "^7||^8||^9") is gone. It is
!! not really: eslint-config-next depends on eslint-plugin-react, whose LATEST release 7.37.5 peers eslint "...||^9.7" and still
!! calls the context.getFilename() API that ESLint 10 REMOVED. With eslint 10 installed, `npm run lint` dies with
!! "TypeError: contextOrFilename.getFilename is not a function" while loading rule 'react/display-name'. There is no newer
!! eslint-plugin-react to override to. Re-test when one ships eslint 10 support.

!! THE "sharp": "^0.35.0" OVERRIDE STAYS -- STILL LOAD-BEARING ON 16. next@16.2.12 STILL declares optional "sharp": "^0.34.5",
!! and the advisory (GHSA-f88m-g3jw-g9cj, CVE-2026-33327/33328/35590/35591) is `sharp <0.35.0` -- the WHOLE 0.34.x line. Removing
!! the override reintroduces a high. Re-test only when a next 16.x ships a sharp ^0.35 range.

== OTHER THINGS FOUND 2026-07-26, worth knowing but NOT urgent

eslint 10 on the server adds `preserve-caught-error` to its recommended set. It caught a real bug in utils/googleAuth.js
(a JSON.parse failure was rethrown without `cause`, losing the parse position -- now fixed). EXPECT THIS RULE TO FLAG MORE
bare rethrows as older files get touched. The fix is always the same shape: throw new Error(msg, { cause: e }). It is a
genuine improvement, not lint noise -- don't disable the rule.

price_change_log holds rows where old_price = new_price. These are NOT a bug and NOT review-date updates (pricing-park writes
no log row at all). They are HOLDS: Apply pressed with the price left unchanged, which is the only way to record WHY a style
was left alone, because park sets the review date but stores no note. The Analytics > Price Changes "Impact" panel counts them
in its Holds column. DO NOT add an old==new guard to pricing-apply -- it would discard the note, which is the whole point of
the action. If a cleaner route is ever wanted, let pricing-park accept a note; be aware that would move holds out of
price_change_log and change what the activity summary counts.

Watch for accidental double-Applies. 1015399-BARBADOS logged the same no-op twice, 18s and 57s after a genuine raise, same
note each time (ids 1772/1773, to be deleted). If that pattern recurs it inflates the Holds count with things that aren't
really analysis, and may mean Apply isn't confirming clearly enough that it worked.
